# Audit complet du hub et du CT PHP, nuit du 26 au 27/10/2026

Base : `main` 997a2c2. Branche : `audit/2026-10-27` (commits locaux, rien poussé, rien posé sur les CT ni en production). Aucune migration écrite.

## Résumé pour Alexandre

1. Rien de grave n'est ouvert de l'extérieur : connexion, double authentification, sessions, garde d'origine et contrôle d'accès des routes sont solides.
2. Le défaut le plus sérieux concernait les sites PHP entre eux : un site malveillant pouvait faire afficher le fichier `.env` (mots de passe) d'un autre site. Corrigé cette nuit.
3. L'import ou la restauration d'une base SQL pouvait exécuter des commandes du client MariaDB en tant qu'administrateur du serveur PHP. Corrigé (mode « bac à sable »).
4. Avec le mot de passe, quelqu'un pouvait essayer bien plus de 5 codes à 6 chiffres en les envoyant tous en même temps. Corrigé : 5 essais au plus, même en parallèle.
5. Un site PHP qui n'existait plus sur le serveur PHP ne pouvait plus être supprimé du hub. Corrigé.
6. Une mise à jour du hub ratée au milieu des migrations pouvait le relancer sur une base à moitié migrée. Corrigé.
7. Gros fichiers (jusqu'à 256 Mo) : le navigateur les chargeait en entier pour les vérifier (risque de plantage sur téléphone). Corrigé.
8. Restent des points à décider avec toi, sans urgence (liste « proposé » ci-dessous) : surtout le cas d'une version PHP refusée pour fuite, la surveillance en cas de coupure de ta box, et la vérification des mises à jour venues de GitHub.
9. Tous les tests passent (voir « Tests »), avec les nouveaux tests de chaque correction.
10. Après relecture et push, une seule chose à faire : `hubctl update` (met aussi à jour le serveur PHP). Rien d'autre à régler.

## Méthode

Lecture réelle du code par domaine (cinq lectures en parallèle, plus un relecteur indépendant pour l'agent PHP), puis vérification de chaque constat dans le code avant toute correction. Corrections seulement pour les P0 et P1 évidents et sûrs, chacune avec un test qui échoue sans elle (sauf `update.sh`, voir plus bas). Gravité : P0 exploitable ou cassé, P1 sérieux mais conditionnel, P2 durcissement ou finition.

Aucun P0 trouvé.

### P2 (finition, durcissement)

- Agent PHP :
  - la sonde du contrôle anti-fuite est écrite en root dans un dossier du site ; impact faible, nom aléatoire et contenu fixe (`sites.mjs:726-736`). Proposé : écriture sous le compte du site ;
  - les nonces de signature ne sont gardés qu'en mémoire : un rejeu dans les 60 s qui suivent un redémarrage de l'agent est possible (`agent.mjs`). Proposé : refuser les horodatages antérieurs au démarrage ;
  - le capteur SMTP garde jusqu'à 25 Mo par connexion en mémoire, avec 20 connexions, dans l'agent root hors cgroup (`mail.mjs:278-307`). Proposé : écrire en flux sur disque ;
  - aucune borne sur la taille décompressée d'une archive (`sites.mjs:618-631`). Seul le hub, de confiance, peut en envoyer.
- Hub, sécurité :
  - cookies sans préfixe `__Host-`, alors qu'ils sont partagés avec les sous-domaines clients : un site client peut poser un cookie qui gêne la session (déni de service, pas de vol de session) (`lib/auth.ts:7`, `:74-83`) ;
  - trois GET ont des effets de bord (export PDF, export de production, dump de base) et sont déclenchables depuis un sous-domaine client, sans pouvoir lire la réponse (`routes/monitor.ts:262-284`, `routes/maintenance.ts:86-118`, `routes/php-site.ts:231-247`) ;
  - erreurs 4xx journalisées avec leur pile, et `ZodError` détaillée renvoyée au client (`lib/http.ts:61-68`) ;
  - déchiffrement AES-GCM sans longueur de tag imposée (`lib/crypto.ts`, `createDecipheriv` sans `authTagLength`) ;
  - challenges 2FA gardés au changement de mot de passe (`scripts/admin-create.ts:51-53`) ;
  - cookie gardé à la déconnexion sans session valide (`routes/auth.ts:176`).
- Hub, logique :
  - une version PHP en échec reste « en cours d'envoi » jusqu'au redémarrage (`php-sites.ts:75-113`) ;
  - restauration d'une version sans verrou, en concurrence avec la purge (`routes/sites.ts:341-351`) ;
  - une session d'envoi reste cassée après un échec non HTTP de l'import (`uploads.ts:361-367`) ;
  - disque plein pendant l'extraction d'un zip (`uploads.ts:228`, `zip.ts:144-162`) ;
  - un CREATE ne peut plus être repris après une publication (`operations.ts:323-324`) ;
  - vignette écrite après la suppression du site (`thumbnails.ts:143-144`).
- Surveillance et e-mails :
  - une panne SMTP de plus de 30 min fait sauter des e-mails redirigés : la place du débit est prise avant l'envoi (`php-mails.ts:243-246`) ;
  - incidents en double sur « Contrôler » pendant un cycle (`routes/monitor.ts:236-241`) ;
  - `/sync` du Worker refusé en entier pour un seul abonnement hors limites (`routes/push.ts:134`) ;
  - envoi push sans délai (`lib/push/service.ts:44`) ;
  - l'historique d'un site suit la cible après un changement de domaine (`monitor/targets.ts:34-46`).
- Exploitation :
  - les clés privées de licence ne sont pas dans la sauvegarde (`scripts/alpine/backup.sh:161-164`) : perdre le CT du hub, c'est ne plus pouvoir signer de licence ;
  - `cloudflared` est installé sans empreinte vérifiée (`configure.sh:62`) ;
  - la réponse de l'ERP n'est pas authentifiée (`lib/erp/http.ts:79-99`).
- Interface :
  - fausse réussite de « Reprendre la capture » quand le site n'a pas encore de vignette (`ThumbnailTab.tsx:43`, `:67`) ;
  - suppressions sans confirmation : e-mail capturé, vignette d'un logiciel, « Annuler cet envoi » ;
  - double envoi possible au retrait d'un appareil de notification ;
  - focus perdu pendant une confirmation en cours (`ConfirmDialog.tsx:44-48`) ;
  - tableaux empilés sous 768 px sans rôles ARIA ;
  - halo de focus faible des champs (`Field.tsx:48`).
- Performance :
  - catalogue en N+1 (`site-view.ts:154`) ;
  - sondages qui continuent quand l'onglet est caché ;
  - toutes les icônes dans le fichier chargé au démarrage (`vite.config.ts`) ;
  - archive vers l'agent lue blob par blob en mémoire (`tar.ts:61`).

### Déjà couvert (vérifié, rien à faire)

- Toutes les routes passent par la validation zod.
- Les téléchargements sont en `octet-stream`, avec `Content-Disposition` assaini et CSP `sandbox`.
- Signature hub et agent :
  - HMAC sur la méthode, le chemin, le corps et l'horodatage ;
  - fenêtre de 60 s, anti-rejeu, comparaison à temps constant ;
  - empreinte d'archive vérifiée avant lecture ;
  - opérations fermées, chaque paramètre validé ;
  - archives contrôlées (ni lien, ni `..`, ni chemin absolu) ;
  - commandes sous le compte du site ;
  - fichiers générés construits depuis des valeurs validées ;
  - pare-feu des sites par UID ;
  - MariaDB : un compte par base, `local-infile=0`.
- Zip côté hub :
  - zip slip, liens et fichiers chiffrés refusés ;
  - tailles comptées sur le contenu réellement décompressé ;
  - doublons refusés.
- Signature hub et Worker de surveillance : HMAC en temps constant, horodatage croissant. Push limité à une liste blanche de services.
- E-mails capturés : HTML isolé (sandbox sans scripts, CSP `default-src 'none'`), mot de passe SMTP jamais renvoyé.
- Licences : JSON canonique revérifié, identifiant jamais réémis, suppression journalisée.
